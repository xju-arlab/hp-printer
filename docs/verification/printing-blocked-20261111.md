## 访问与观测

管理入口使用本机已配置的 `ssh pi4`，确认目标主机为 `fourb`。该入口在当前电脑无法直连 `192.168.5.87` 时仍可用。凭据不记录在文件中。

- 公网状态接口 HTTP 200；cloudflared、hp-printer、CUPS、ipp-usb 均运行。
- 当前 Mac 没有新作业；Windows 提交的 CUPS 258、259 已到达树莓派，两者同名、同大小（约 83 KiB），解压后的文件并不完全相同，不应自动认定是重复文件并删除。
- 258 为单页 A4 PDF，Ghostscript 转换已成功结束；服务器磁盘空闲约 40 GiB。
- CUPS 258 的完成页计数曾显示 1，但打印机内部作业 13 实际报告完成页数 0、仅处理约 8 KiB，长时间处于 processing。设备报告 `spool-area-full-report` 并停止接收新作业。内部作业创建时间 15:15:26 UTC，与 CUPS 258 的创建/开始时间吻合。
- USB 数据上传停滞，第三个接口有未完成传输，其他接口仍能返回状态。此证据定位到 USB/打印机接收路径，不能据此确认具体固件缺陷或已成功出纸。

## 已执行

1. 将打印队列暂时暂停，保留 258、259 两个任务；配置备份到树莓派 `/var/backups/hp-printer/20261111-usb/`，包含 printers.conf、PPD、ipp-usb.conf。
2. 重启 ipp-usb。随后初始化反复超时；日志显示打印属性查询成功，但传真探测返回 HTTP 405，扫描探测超时，导致重复 USB reset。
3. 为该型号增加 `/etc/ipp-usb/quirks/hp-deskjet-4900.conf`：禁用传真探测，只用一个 USB 接口。`ipp-usb check` 通过，初始化及状态查询恢复。仓库副本见 `deploy/ipp-usb-hp-deskjet-4900.conf`。这是本次观察支持的恢复措施，尚未验证实际打印及扫描行为。
4. 在确认打印机内部作业 13 仍为同一创建时间、实际完成 0 页后，尝试取消这个未完成的设备接收任务；设备返回 IPP `0x0403`，请求未成功。没有删除 CUPS 上的原任务。
5. 用户暂时无法现场重启打印机。已重新启用 CUPS 队列，让设备恢复后继续处理原任务；结束时原任务仍在队列，设备内部作业仍卡住。

## 后续恢复与验收

需要现场将打印机正常关机、断电等待约 30 秒后重新开机，树莓派保持运行。通过 `ssh pi4` 复核 USB 状态、原 CUPS 作业及设备实际完成页数。避免再次提交同样文档；两个原任务可能在恢复后依次打印。

必须分别确认 CUPS completed 和实际出纸。本次不能标记为“修复成功”。如果重启后同类传输再次卡住，再在受控条件下检查 raster/gzip 传输兼容性，不能把未验证的压缩设置改动当作已确认修复。

## 配置回退
