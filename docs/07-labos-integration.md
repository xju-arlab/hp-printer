# 07 LabOS 对接边界

[返回主计划](README.md) · [队列与 API](03-queue-and-api.md)

## 1. 独立项目优先

用户明确新建 `hp-printer` 专门承载打印后端，并指定纯 Python + uv 项目，支持 CLI 打印，不开发前端。打印应在没有 LabOS、统一登录、云端消息代理的情况下独立工作；Windows 原生入口和 CLI 共用 CUPS 队列。

相邻 xju-lab 的[原概要架构](../../xju-lab/docs/plan/02-architecture.md)曾提出同仓 `printer-agent/`、WSS Agent 和业务队列。对于本次打印实现，以下新决策优先；旧 LabOS 文档后续接入打印阶段时再同步，不要求当前前端原型修改。

| 原先设想 | 本次确定/建议边界 |
|---|---|
| xju-lab 内的 printer-agent | 独立 `hp-printer` 工程，独立部署和发布 |
| 先由 LabOS 后端调度打印 | 先由 Pi CUPS 统一接收 Windows 和 API 任务 |
| 必须主动 WSS 到云端 | LAN 第一版不依赖 WSS；远程阶段再选网络方案 |
| 所有打印入口 PDF only | CLI/管理 API 首版限制 PDF；原生 Windows 遵循协商格式 |
| LabOS 队列是设备执行权威 | CUPS 是执行权威；LabOS 保存业务申请与关联状态 |
| 直接把 Windows 用户名当成员 | 原生用户名自报，不等于 auth-login 的可信主体 |

## 2. 模块责任

| hp-printer | LabOS |
|---|---|
| USB、驱动、CUPS、设备能力与故障 | 成员、实验室、业务表单、审批和通知 |
| 稳定打印入口、CLI 和统一执行队列 | 文档来源、业务授权、页面导航 |
| 原生任务同步、提交幂等、管理员控制 | 业务请求 ID、文件授权、打印结果投影 |
| Pi 安装/升级/诊断/容量与文件清理 | 云端数据保留、用户及项目关系 |

后续 `LabOS printing` 模块不能再运行一个定时器，把已提交的 CUPS 任务按旧业务状态重发。业务任务应同时保存 hp-printer submission ID、print_job UUID、最终 CUPS 标识；以提交幂等键连接两个系统。

## 3. 后续集成接口

LabOS 后端使用受限服务身份调用 `/api/v1`，先查询能力，再提交有权访问的 PDF 文件流。每个业务打印申请使用稳定幂等键，不在浏览器暴露 Pi 管理令牌；hp-printer 不接受未经约束的文件下载 URL。

LabOS 登录使用用户已指定的 `Projects/auth-login/` 体系。此身份体系属于 LabOS 的既有决定，不是本项目首版依赖。后续接入时，服务间身份与被代表用户分开记录；若传递 `iss/sub`，必须由可信服务声明或经过签名验证，不能相信任意请求头。

首版后续集成可通过查询获取状态；需要推送再实现带签名、事件 ID、重试和去重的 webhook，接收方通过查询核实最终状态。业务通知不影响 CUPS 输出；事件投递失败不重打文档。

## 4. 配额、审批和身份限制

如果 LabOS 要求审批或强制个人配额，而 Windows 仍可匿名直达 CUPS，业务规则会被绕过。不能只在网页添加审批按钮就声称限制了所有打印。此类要求需另做认证 IPP、入口限制或统一提交策略设计，并由 Windows 实验验证可用性。

第一版用户已经选择自动打印，不引入审批流。管理服务对原生任务仅保存自报用户名及其低置信度；准确个人统计、计费和本人取消属于后续需求。

## 5. 远程访问

远程阶段先明确客户端位置、网络可达性、认证与访问范围，再选 VPN/受控隧道/网关方案；不把 CUPS 或管理员 API 直接端口转发到互联网，也不预设会采购云打印服务。

无论采用何种远程路径，统一队列、提交不确定时对账、停止接收与暂停执行分开这几项约束保持不变。远程方案的测试独立于 LAN 首版验收。
