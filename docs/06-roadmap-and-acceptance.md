# 06 分阶段实施与验收

[返回主计划](README.md) · [进度记录](progress.md) · [新对话入口](HANDOFF.md)

## 2. P0：已完成盘点

本轮已核对 Ubuntu/架构、软件版本、USB、队列、能力、地址、CUPS 共享状态、Windows build 和 IppURL 参数。结果见[设备基线](00-current-device.md)。

仍未完成的部署备份和真实打印验收归 P1，不把本轮只读访问扩写成“全链路测试通过”。再次开始工作只需简短复核变化，不重复安装 CUPS/ipp-usb。

## 3. P1：Windows 接入（主链路已验证，收尾项保留）

| 子步 | 工作 | 验收证据 |
|---|---|---|
| P1.1 | 复核设备并备份；调查重复 IPP 属性 | 备份位置已记录；重复发生于 CUPS 生产队列响应，临时对照仍未发现具体合并原因 |
| P1.2 | 以限定接口和网段共享唯一队列 | 当前 WLAN 的 TCP 631 可达；`/admin`、`/admin/conf` 返回 403；TCP 60000 对 LAN 不可达；直连接口不监听 CUPS |
| P1.3 | 在 Windows 添加新系统打印机并检查默认值 | build 26200；使用系统内置 Microsoft IPP Class Driver；原 USB/WSD 队列和默认值保留 |
| P1.4 | 提交少量非敏感测试页 | Windows job 4 → Pi CUPS job 3；Validate/Create/Send 均成功，CUPS 报告完成；用户确认测试页实际出纸 |

Windows 已证明当前 build 可通过 Microsoft 内置 IPP 类驱动提交作业，无需 HP 厂商驱动；用户确认测试页实际出纸。此结果只代表本次组合互通，不代表重复属性符合 RFC 8011，也不代表所有 Windows/应用兼容。严格检查仍失败，稳定 WLAN 地址、IPP `Get-Jobs`/`Get-Job` 权限、Word/PDF 和 protected print 仍未验收；P1 主链路与本次实物出纸可支撑进入 P2，整体 P1/发布验收仍保持未完成。不得关闭 Windows protected print 或改动原有打印机来掩盖兼容问题。

## 4. P2：后端只读核心

P2.1 建立根目录 uv 包工程：pyproject.toml、uv.lock、.python-version、src/hp_printer/，配置 CLI console script、默认/server/dev 依赖边界；实现 help/version/serve 和配置加载。接管队列白名单，验证 Pi arm64 原生依赖；本地开发提供有明确标记的 fixture adapter。

P2.2 实现 CUPS 查询适配、能力归一化、超时/不可用处理和版本化契约，同时提供 printers list、printer status/capabilities、jobs list/show。单元测试覆盖缺失属性、未知原因、同名异队列、CUPS 不可达。

P2.3 建 SQLite 迁移和单实例对账 worker；导入已有原生 IPP 任务。验证进程重启、历史消失、任务 ID 冲突不会覆盖旧记录或触发打印。

通过标准：真实设备状态/能力和 CUPS 对应，接口标注同步时间；原生 Windows 任务能被导入；停止后端不影响已进入 CUPS 的打印。模拟设备数据不能当实机通过证据。

## 5. P3：管理员控制

先实现 CLI auth init-admin/login/status/logout、令牌期限/撤销及只读/控制权限，再实现单任务取消、挂起/释放和队列暂停/恢复、接受/拒绝的 API 与命令。每个动作有 operation ID 和审计；状态冲突重新读取，未知结果不显示成功。

通过标准：匿名/普通客户端不能跨用户控制或下载文件；对已终结任务的“恢复”被拒；并发取消/恢复不会产生新打印副本；正在打印的取消显示可能已输出部分页。CUPS/DB 故障时控制结果有可追踪状态。

## 6. P4：可靠提交

实现 `uv run hp-printer print FILE.pdf`，客户端先持久化 request ID，服务端完成 PDF 流式验证和临时文件生命周期，再实现持久化意图 → CUPS 暂存任务 → 文档接收 → 自动释放。依据[提交详细设计](03-queue-and-api.md)和[CLI 契约](08-cli-and-uv.md)做故障注入。

必须验证：相同幂等键重复请求、不同文件同键、创建返回丢失、上传返回丢失、释放返回丢失、各步骤进程崩溃、磁盘不足和恶意参数。没有可确定的上游结果时标记待核验，不重建作业。

通过标准：每个已确认接收的 submission 能映射到同一个 CUPS 作业；重试没有第二次意外物理输出；无法确定的情况会明确阻止自动重试。支持选项经 Validate/实际任务核对，不只测试 JSON 接收。

## 7. P5：CLI 完善与打包

将 P2–P4 已实现命令统一为稳定 CLI：全局参数、配置优先级、JSON Schema、错误码/退出码、等待超时/中断、幂等键查询、doctor、完整帮助和使用示例。命令详见 [08](08-cli-and-uv.md)，不新增前端工程。

输出覆盖空队列、离线、权限不足、同步过期、取消请求中和操作失败；暂停执行/停止接收分开；耗材未知不显示成 0%。默认返回接收回执，--wait 不把服务报告完成等同于人工出纸确认，Ctrl+C 不取消服务端任务。

通过标准：uv lock --check、相关 pytest/静态检查及 uv build 通过；构建包在独立环境、非源码目录能执行 CLI；JSON stdout 可解析、错误退出码准确；Pi CLI 实机打印与 Windows 共用队列。CLI 测试不依赖前端或 Node。

## 8. P6：部署与故障矩阵

安装器、Windows 工具按[运维文档](05-deployment-and-operations.md)实现；只有执行成功过的脚本才能写为已支持。

| 场景 | 核心验收 |
|---|---|
| 重复安装、配置已有人工修改 | 幂等或清楚报冲突，不覆盖他人配置 |
| 升级失败、数据库迁移失败 | 配置/服务可回退，活动打印队列仍在 |
| 后端崩溃、CUPS 重启 | 不重放旧任务，恢复后状态可对账 |
| USB 拔插、缺纸、设备关机 | 原任务可解释；恢复不盲目重打 |
| Pi 断电重启 | 无无限重试；不确定物理输出显式标识 |
| 磁盘低水位、大文件、连续任务 | 原生/HTTP 两个入口都有容量保护 |
| 两台 Windows 同时提交 | 同一权威队列，任务归属置信度准确 |
| 未授权 LAN/CLI/API 请求 | 管理/文件读取被拒，令牌过期/撤销有效，日志有界且脱敏 |
| 移除客户端、卸载服务 | 不影响其他打印机、驱动和系统 CUPS |
| 地址变更、内部代理端口变化 | doctor 能定位层次，给出保留队列的修复路径 |

网络中断与断电测试在约定窗口和非敏感测试任务上执行，记录页数与可能重复输出。持续运行建议观察一个工作日，监测指标无异常后再作为常用打印入口。
